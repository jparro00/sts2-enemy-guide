# Spire Codex — STS2 Enemy Reference (spirecodex.com)

Unofficial Slay the Spire 2 reference site. Static GitHub Pages deploy — **no framework, no npm, no bundler**. Runtime is plain global-scope JS; the only build steps are Python (SEO snapshots + image thumbnails) and they run in CI, not locally.

## Architecture in 30 seconds

- **Runtime SPA**: `index.html` loads `js/*.js` (plain scripts, global state — load order in `index.html` matters). `js/data.js` fetches `data/*.csv` + `site-config.json` at page load; `js/renderers.js` + `js/panels.js` build the HTML strings, `js/ui.js` wires them to the DOM.
- **Build-time SEO snapshots**: `build_snapshots.mjs` (Node) renders every enemy/encounter/event into static pages under `enemy/`, `encounter/`, `event/` + `sitemap.xml`. It loads the *actual browser scripts* via `node:vm`, so there is exactly **one rendering implementation** — a change to `js/renderers.js`/`js/panels.js`/`js/data.js` automatically applies to both the live SPA and the snapshots. Keep panel/renderer code DOM-free (strings in, strings out); DOM access belongs in `js/ui.js` only, which the snapshot build never loads.
- **Deploy** (`.github/workflows/deploy.yml`) is the real build entry point: `python build_thumbs.py` → `node build_snapshots.mjs`. Dependencies: Pillow + Node (both preinstalled on the runner).

## Critical facts (read before touching anything)

1. **`data/` is the canonical, hand-maintained data source.** The runtime fetches it directly. (A legacy `csv/` directory + Excel bootstrap pipeline was archived to `../sts2_archive/` — if you see references to `csv/`, `build_csvs.py`, `build_html.py`, or `data/enemies.csv`/`moves.csv`, that's the dead pipeline.)
2. **Editing `data/*.csv` requires NO local build.** The SPA reads CSVs at runtime; snapshots regenerate at deploy. Local preview: `serve.bat` (http://localhost:8080).
3. **`index.html` and `404.html` are simultaneously source files and build templates.** `build_snapshots.mjs` regex-rewrites the version banner and `<base href>` and writes them back. Version strings in the checked-in copies look stale — they are runtime-replaced placeholders, not bugs.
4. **`enemy/`, `encounter/`, `event/`, `sitemap.xml` are gitignored build output.** Local copies may be stale (possibly built with a beta `<base href>`). Never edit them; never trust them as current.
5. **`site-config.json`** holds `gameVersion` / `betaVersion` / `isBeta`. Locally and on beta branches `isBeta` is true; deploy forces it false on master. This local/production mismatch is intentional.
6. **`spine_godot/` is untracked but REQUIRED infrastructure** for the render-sprite / render-sprite-vfx skills. Never delete it during cleanup. Same for `raw/` (decompiled game source, regenerated by the beta-pipeline / lookup skills).
7. **Data lives on display names.** Enemy images must be `media/enemies/<exact display Name>.webp`; `monster_moves.csv` joins on the `Enemy` column; slugs derive from names. Renaming an enemy breaks images (silently — every `<img>` has `onerror` hide), moves, and deep links at once.

## Branch topology & push rules

| Branch | Deploys to | Notes |
|---|---|---|
| `master` | site root (live) | `isBeta` forced false at deploy |
| highest `beta-v*` | `/beta/` | only the highest version number deploys; older beta branches are retired |
| `test` | `/test/` | noindex forced; **always safe to push** |

- **NEVER push `master` or any `beta-v*` branch without explicit user approval.** Committing is always fine; pushing is the dangerous act.
- Shared build/UI files (`build_snapshots.mjs`, `js/`, `css/`, `index.html`, `deploy.yml`) must be kept in sync across master and the active beta branch — data files (`data/*.csv`, `site-config.json`) intentionally differ.
- Full pipeline for applying a game beta patch: use the `/beta-pipeline` skill (it documents decompilation, patch-note cross-referencing, and the branch/file sync matrix in detail).

## Data conventions

CSV schemas and the micro-syntax used inside cells (`{power_key}` refs, `<Move Name>` refs, `[coop]`/`[info]`/`[bug]`/`[req]` note tags, lore bbcode, `N (M)` ascension values, split conventions) are documented in **`data/README.md`**. Read it before editing any CSV.

## Common tasks

| Task | What to do |
|---|---|
| Update enemy stats/moves | Edit `data/monsters.csv` / `data/monster_moves.csv`. No build needed. |
| Add/update an event | `data/events.csv` + `data/event_choices.csv` (joined on event `Key`). |
| Add enemy art | Use the `/render-sprite` skill → outputs 512×512 webp to `media/enemies/`. |
| Look up game mechanics | Use the `/lookup` skill (decompiles live from the game PCK). |
| Apply a game patch | Use the `/beta-pipeline` skill. |
| Preview locally | `serve.bat`, then http://localhost:8080. User prefers to test UI changes themselves — don't screenshot/preview-verify UI on their behalf. |
| Rebuild snapshots locally (rarely needed) | `rebuild.bat`, or `python build_thumbs.py` + `node build_snapshots.mjs` — expect `index.html`/`404.html` to get cosmetic diffs (see fact 3). |

## Code conventions

- JS: plain scripts sharing globals (`js/config.js` declares state; `js/data.js` loads and auto-runs; `js/ui.js` renders). No modules — script order in `index.html` is load-bearing.
- No HTML escaping: CSV content flows into `innerHTML`. Data is first-party, but avoid `"`, `<`, `>` in names.
- Comments explain *why*, not *what* — keep that standard.
- No tests. The only build guard is `build_snapshots.mjs` failing if it generates < 50 pages. Verify data edits by loading the site locally.
